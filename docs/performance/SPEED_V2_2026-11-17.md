# Speed pass V2: why pages open slowly (2026-11-17)

Measured on production (built2bid.org) over the last 7 days of Netlify request logs, Supabase edge
logs and `pg_stat_statements`.

## What we found

| Area | Measurement | Verdict |
|---|---|---|
| Typical page, warm server | Real Chrome users: p50 0.12 s, p75 0.23 s | Fine |
| Cold starts | p99 4–6 s on every server page (e.g. `/dashboard/customers` 6.7 s: 1.7 s Node boot, Sentry init, then a cold render) | **Main cause of "sometimes very slow"** |
| No loading screens | Zero `loading.tsx` files: a click shows nothing until the whole server render finishes | **Main cause of "feels slow"** |
| Dashboard | p50 0.20 s, p75 0.69 s, p90 1.2 s. Six database rounds in a row (each 50–100 ms) + layout bookkeeping | Fixable in code |
| Sign-in checks | `/auth/v1/user` called 6,883×/day: layout, page and helpers each re-checked the session | Fixable in code |
| Layout bookkeeping | `leads` lookup (p50 248 ms) blocked every signed-in page | Fixable in code |
| Notification bell | `/api/notifications` p50 0.67 s (runs a sync write each call). Runs after the page shows, every 5 min | Minor |
| Supabase region | us-east-1; Netlify functions default us-east-2. ~10 ms apart | Fine |
| Supabase size | Micro compute, 23 MB DB, 11 users, 23 estimates | Indexes don't matter yet; queries are 20–60 ms of RLS/function overhead |
| Supabase advisors | 147 unindexed FKs (INFO), 2 RLS initplan warnings, 4 duplicate SELECT policies | Not a speed factor at this data size; revisit at ~10k rows |
| Netlify plan | Free (`nf_team_dev`) | Paid plans don't make functions faster or remove cold starts |
| Home page `/` p50 0.6 s | Skewed by the Better Stack uptime bot (8,547 hits/week, p50 0.71 s from its probe region). Real users ~0.12 s | Fine |

## Fixed in this PR (no SQL, no settings)

1. `loading.tsx` skeleton for every signed-in page and the admin area: the click answers instantly.
2. `getAuthUser()` is cached per request (React `cache`): one Auth round trip per page, not 3–4.
3. App layout: lead-attribution + referral bookkeeping runs in `after()`, after the page is sent.
4. Dashboard: 13 independent reads go out in one parallel batch instead of six rounds in a row.
5. Server Sentry loads in the background, so it no longer delays cold starts. Errors still reported.
